# A2A 面威胁模型（草案，待评审）

> 状态：**草案，未评审**。按 `方案.md` 的硬门槛，M4/M5 的 A2A 实现必须在本文评审通过后才开始。
> 本文描述的是将要实现的控制项，不是已经实现的保证。

## 1. 范围

本模型覆盖 `nuclear-dev-bot` 的 A2A 远程 V&V：

- 客户端：开发方委托 V&V、接收产物。
- 服务端：独立 V&V 组织接收任务、返回报告与证据包。
- 入站隔离区、来源账本、审计日志。

不覆盖：宿主 Agent 自身安全、操作系统与文件系统安全、人员身份系统、监管审查流程。

## 2. 资产

| 资产 | 分类 | 说明 |
|---|---|---|
| 项目产物 | C2 | 七阶段 JSON、追溯图、证据索引 |
| 证据文件 | C2 | 构建日志、测试记录、V&V 报告 |
| SBOM | C2 | 依赖与版本，单独视为供应链情报 |
| 运行环境指纹 | C2 | 编译器、OS、容器、内部路径 |
| 源码 | C3 | 默认禁止外发，仅双人特批 |
| 算法模型与方程 | C3 | 含离散格式、稳定性与误差分析 |
| 参考解实现 | C3 | 直接暴露算法，默认禁止外发 |
| 参考解结果数据 | C2 | 基准值、误差指标、收敛数据；受接收方与许可约束 |
| 基准题数据 | C3 / 不可转让 | 默认不发；许可禁止转发时标记 `non_transferable`，任何特批无效 |
| 基准题引用标识 | C1 | 名称、版本、DOI；只发引用，不发数据 |
| 人员与组织信息 | C3 | 姓名、资格、组织关系（PII） |
| 安全分级与门禁结论 | C3 | 暴露安全重要性与合规缺口 |
| 批准文件 | 禁止外发 | `.nuclear-dev/approvals/*.json`，任何情况不得进入委托包 |
| 批准人 credential | 禁止外发 | 签署效力相关，必须留在本地 |
| 身份凭据 | 禁止外发 | 访问对端 A2A 服务的 token |
| 审计、provenance、任务账本 | 禁止外发 | 本地追责材料，不是协作内容 |
| 导出清单本身 | C2 | 文件名、结构、数量、哈希可反推项目信息 |
| 对端 agent card / 证书指纹 | C1/C2 | 协作关系与网络拓扑 |
| 入站人员信息（对端执行者/审核者） | C3 | 接收后最小化存储，仅保留签署与独立性所需字段 |

### 2.1 分类与导出规则

| 分类 | 内容 | 形态 | 授权 | 入口 |
|---|---|---|---|---|
| C0 | 工作流、公开标准引用 | 原文或投影 | 清单 + 记录 | CLI / MCP |
| C1 | Schema、通用门禁说明 | 原文或投影 | 清单 + 记录 | CLI / MCP |
| C2 | 项目产物、证据摘要、SBOM、环境指纹 | **必须投影** | 一次性令牌 | CLI / MCP |
| C3 | 源码、模型、基准题、人员、安全分级、门禁结论 | 仅原文特批 | 双人 EXP + 一次性令牌 + TTY 确认 | **仅 CLI** |

默认拒绝。策略按**接收方**索引：同一 C2 文件对 V&V 组织 A 可发、对 B 不可发。

### 2.2 导出机制

- **投影优先**：本地真值不直接打包。投影器按白名单生成 `vv-input-package/`，含脱敏、路径改写、逐项分类与清单。
- **C3 特批**：`export-approvals/EXP-*.json` 由两名不同组织的真实人员独立签署；逐文件哈希、用途、接收方指纹、过期时间。bot 只能校验和消费，**不提供创建命令或工具**。
- **一次性令牌**：`authorize` 由人执行，要求 TTY 与手动确认，绑定清单摘要与接收方；消费时逐文件重算哈希并原子标记已用。
- **永不导出**：批准文件、批准人 credential、身份凭据、审计/provenance/任务账本。
- **安全分级外发**：使用脱敏 `scope_label`，不发送原始 `safety_classification` 字段与分类依据。

### 2.3 基准题与参考解

| 对象 | 处理 |
|---|---|
| 基准题**引用标识**（名称、版本、DOI） | C1，可随投影包发送，用于声明验证依据 |
| 基准题**数据** | 默认不发。三种情况：对端是提供方 → 只发引用标识；许可允许转发 → 双人 EXP 特批；许可禁止转发 → 标记 `non_transferable`，**任何特批都无效** |
| 参考解**实现** | C3，与源码同规则，双人 EXP + 仅 CLI |
| 参考解**结果数据**（基准值、误差指标、收敛阶） | C2，可进入投影包；但仍受接收方策略与第三方许可约束 |

`non_transferable` 优先于所有授权：即使 EXP 齐全、令牌有效，工具也必须硬拒绝。

### 2.4 控制强度的诚实说明

同机同用户且 Agent 具备 shell 权限时，一次性令牌是**流程控制**，不是密码学边界：Agent 理论上可以调用生成令牌的命令。TTY 检查与手动确认能挡住自动化调用，但不能证明操作者一定是人。真正的保证需要 OS 用户隔离、外部审批服务或硬件密钥托管，本包不提供。

## 3. 信任边界

```text
开发方主机（可信）── MCP/CLI ── 本地项目（受控）
        │
        │ HTTPS（不可信网络）
        ▼
V&V 组织 A2A 服务端（半可信：独立治理，但仍是外部系统）
        │
        ▼
入站隔离区（不可信输入）── 校验后 ── 本地证据登记（人工确认）
        │
        ▼
人工批准（系统外，唯一具有约束力的动作）
```

- 网络一律视为不可信。
- 对端 agent 的声明（组织、独立性、结果）一律视为**声明**，不是事实。
- 入站文件一律视为恶意输入，直到校验通过。
- 人工批准是唯一不能被协议替代的动作。

## 4. 威胁与控制

### T1 路径穿越与隔离区逃逸

**场景**：入站包内含 `../../.nuclear-dev/approvals/vv.json`、绝对路径、符号链接、Windows 盘符跳转。

**控制**：
- 解包只允许写入 `.nuclear-dev/a2a/inbox/<task-id>/`。
- 拒绝绝对路径、`..`、空字节、符号链接、硬链接。
- 解包后对每个条目做规范化路径校验，必须仍位于隔离区。
- 单条目大小、总大小、条目数设上限。
- 校验通过前，任何文件不得移出隔离区。

**剩余风险**：文件系统竞态（TOCTOU）。缓解：先解包到随机临时目录，校验完成后再整体重命名。

### T2 资源耗尽与入站体积

**场景**：压缩炸弹、超大文件、海量小文件、超深目录、超长 JSON、慢速请求。

**原则**：A2A 传判定与指针，不传大块字节。`text` / `data` part 内联并受小上限约束；`file` part 只放 `{name, size, sha256, transfer_id}`，**不放字节**；实际内容走带外通道。

**默认上限**：

| 项 | 默认 | 硬上限 |
|---|---|---|
| JSON-RPC 请求 / 响应体 | 4 MiB | 8 MiB |
| `text` / `data` part 单条 | 1 MiB | 2 MiB |
| `file` part 内联字节 | 不允许 | — |
| 单任务 artifact 数 | 100 | 200 |
| 带外单文件 | 256 MiB | 1 GiB |
| 单任务带外总量 | 1 GiB | 4 GiB |
| 归档解压后总量 | 128 MiB | 512 MiB |
| 归档条目数 | 1000 | 2000 |
| 解压比 | 100:1 | 固定 |
| JSON 深度 / 字符串长度 | 64 / 1 MiB | 固定 |
| 并发任务 / 每对端速率 | 4 / 10 req/min | 16 |

默认值可配置，硬上限不可突破。

**强制点**：

- **不信任 `Content-Length`**：流式读取并累计实际字节，超限立即中止；`Content-Length` 只用于提前拒绝。
- 代理侧 `client_max_body_size` 略高于应用上限，让应用返回结构化错误而不是代理的 413。
- **解包必须流式计数**：逐条目累计条目数、单条大小、总量、压缩比；超限即中止并清理隔离区。
- 拒绝绝对路径、`..`、符号链接、硬链接、设备文件、加密归档、嵌套归档（深度 > 1）。
- JSON 解析限制深度、字符串长度与数组长度；拒绝重复键。
- 超限返回结构化错误（`PayloadTooLarge` / `UnsupportedArchive`），不写部分产物、不截断后继续；审计记录拒绝原因与对端标识。

**带外通道**：

- 通道地址来自本地配置，**不来自消息**；不接受对端提供的任意 URL，避免 SSRF。
- 接收后校验 SHA-256、大小与来源通道白名单；通过后才移出隔离区。
- provenance 记录 `transfer_id`、摘要、通道与时间。

**剩余风险**：

- 带外通道自身的访问控制不在本包职责内。
- 解压比上限可能误伤合法的高压缩文本日志，需要在真实日志上校准。
- 默认值是推荐值，**尚未用真实委托包压测**；上线前必须完成一轮体积与耗时压测再定稿。
- 慢速请求仍可能占用连接，需部署侧反向代理超时与连接数限制兜底。

### T3 来源伪造

**场景**：对端伪造组织、伪造 agent card、伪造 provenance、重放旧任务结果。

**控制**：
- 委托时抓取 agent card，记录组织与凭据指纹，任务期间固定。
- 任务 ID + nonce + 有效期；过期或重复 nonce 拒绝。
- 入站包必须带内容清单与摘要，逐项校验。
- provenance 记录 task id、对端标识、组织、摘要、时间、传输方式。
- provenance 是线索不是证据；证据登记必须由人确认。

**剩余风险**：对端主动撒谎无法在协议层识破。只能靠组织治理、合同与人工复核。

### T4 身份与凭据

**场景**：密钥泄露、长期有效凭据、凭据进入日志、重放与改包。

**控制**：

- 请求认证采用 **HMAC-SHA256 签名**，覆盖 `@method`、`@path`、`content-digest`、`created`、`nonce`（RFC 9421 子集）。
- 时间窗 ±300 秒；nonce 缓存 600 秒；同一 `keyid` 下 nonce 不得重复。
- `Content-Digest` 在 JSON 解析**之前**校验原始请求体。
- 密钥只从文件读取（`--auth-key-file` 或 `NUCLEAR_A2A_KEY_FILE`），不接受命令行明文；日志与审计只记 `keyid` 与指纹。
- 密钥文件**不得位于 workspace 内**，服务端启动时检查并拒绝。
- 双钥轮换：`current` / `next` / `retiring` 三种状态；接受三种，签名只用 `current`。
- 密钥文件按 mtime 热重载；重载解析失败时** fail closed**（返回错误），不继续用旧钥。
- 对端白名单：签名有效不等于授权通过；`allowed_peers` 之外的 `keyid` 一律拒绝。
- 非 loopback 必须 HTTPS；签名保证完整性，不保证机密性。
- 认证失败统一返回 `401`，不区分“keyid 不存在”与“签名错误”，避免枚举。

**剩余风险**：

- HMAC 是对称的，**无不可否认性**；双方都能生成同样的签名记录。
- 密钥泄露即完全冒充，直到轮换完成。
- 同机同用户下，Agent 可以读取密钥文件；这不是本系统能解决的边界。
- 进程重启后 nonce 缓存丢失，时间窗内理论可重放；时间窗是有意压小的。

**密钥文件格式**：

```json
{
  "schema_version": 1,
  "agent_id": "dev-org",
  "allowed_peers": ["vv-org"],
  "keys": [
    {"keyid": "dev-2026a", "peer": "vv-org", "status": "current",
     "secret": "base64(32 字节以上)", "not_after": "2027-01-31T00:00:00Z"},
    {"keyid": "dev-2026b", "peer": "vv-org", "status": "next",
     "secret": "base64(...)"}
  ]
}
```

校验规则：

- `secret` 必须 base64 且解码后不少于 32 字节；
- `keyid` 全文件唯一，且只能含字母、数字、`.`、`_`、`-`；
- `status` 只能是 `current` / `next` / `retiring`；
- `peer` 必须在 `allowed_peers` 中；
- `not_after` 过期即拒用；
- POSIX 上检查文件权限，非 0600 时启动拒绝；Windows 无法用标准库检查 ACL，只能文档要求。

**轮换步骤**：

1. 双方各自新增 `next` 密钥并热重载；
2. 双方把原 `current` 标为 `retiring`，把 `next` 标为 `current`；
3. 观察重叠期内请求全部成功；
4. 重叠期结束后删除 `retiring`，再次热重载。

任何一步解析失败都 fail closed，不沿用旧钥继续服务。

### T4.1 通道与 TLS

**启动规则（硬约束）**：

```text
默认 --bind 127.0.0.1；明文 HTTP 只允许 loopback。
非 loopback 必须满足其一：
  a) --tls-cert + --tls-key                    → 直连 TLS
  b) --trust-proxy-tls 且 bind 为 loopback     → 反向代理模式
否则拒绝启动（退出码 2）。不提供 --insecure 覆盖。
```

**反向代理模式**：

- 仅当 `--trust-proxy-tls` 且 TCP 对端是 loopback 时，才读取 `X-Forwarded-For`、`X-Forwarded-Proto`、`X-Client-Cert-Subject`。
- 审计同时记录 `socket_peer` 与 `forwarded_identity`，不只信转发头。
- 部署要求：TLS 1.2+、`proxy_buffering off`（SSE）、`client_max_body_size` 与应用上限对齐、注入前剥离客户端自带同名头。

**直连 TLS**：

- 最低 TLS 1.2，优先 1.3；密码套件使用 OpenSSL 默认值，不手工挑选。
- 证书或私钥不存在拒绝启动；POSIX 上私钥必须 0600。
- 证书按 mtime 热重载；重载失败 fail closed。
- 可选 `--tls-client-ca` 启用客户端证书校验；不实现 CRL 自动拉取。
- 不实现 ACME。

**客户端**：

- 必须验证服务器证书，默认系统 CA；私有 CA 用 `--ca-file`。
- **不提供跳过证书校验的开关。**
- 可选 `--pin-sha256`，但需在文档中写明与证书轮换的冲突。

**残余风险**：

- 代理配置错误可能把应用端口直接暴露；应用只能靠启动规则兜底。
- 直连 TLS 的协议加固责任在部署方。
- TLS 私钥泄露只破坏通道，攻击者仍需 HMAC 密钥才能通过应用层认证。

### T5 SSRF 与端点劫持

**场景**：客户端被诱导连接任意 endpoint，或配置被替换。

**控制**：
- 客户端 endpoint 来自受控配置，不接受任务参数指定。
- 默认只允许 HTTPS（loopback 例外）。
- 记录实际连接的 endpoint 与证书指纹。

**剩余风险**：本地配置被篡改超出本系统能力。

### T6 数据外发

**场景**：把源码、受控资料或超范围产物发给第三方。

**控制**：
- 默认拒绝，按接收方索引的白名单策略（见 2.1 / 2.2）。
- C2 必须走投影包；清单逐文件列出路径、大小、哈希、分类。
- C3 必须双人 EXP + 一次性令牌 + TTY 确认，且只能从 CLI 发起。
- 批准文件、批准人 credential、凭据、审计/provenance/任务账本永不导出。
- 安全分级用脱敏 `scope_label`；人员姓名默认脱敏，只保留角色与匿名标识。
- 外发清单与摘要写入 provenance 与审计。

**剩余风险**：清单由人确认，误确认仍是主要风险。令牌在同机同用户下是流程控制，不是密码学边界（见 2.3）。

### T7 独立性伪造

**场景**：同一组织同时扮演开发方与 V&V 方，或声明 `independent: true` 与实际不符。

**控制**：
- 服务端启动必须声明 `--organization`。
- 若服务端组织与项目 `developer_organizations` 相同，agent card 标 `independent: false` 并拒绝 V&V 任务。
- bot 不得自动填写 `independent: true`；只能报告组织字段冲突。
- V&V 最终批准人不得是执行者、审核者或开发组织成员（已有内核规则）。

**剩余风险**：组织关系图不完整时无法判定。需人工声明与审查。

### T8 批准边界被绕过

**场景**：A2A 的 `completed` 被当成门禁通过或批准；服务端新增批准接口。

**控制**：
- 协议层与工具层都不存在批准接口。
- `completed` 只表示任务执行完成；门禁必须本地重跑。
- 测试断言：任何入口都不存在 approve/sign 能力。
- instructions、文档、agent card 三处声明该边界。

**剩余风险**：使用者误读。只能靠文档与培训。

### T9 审计篡改

**场景**：删除、修改、截断或整链重写 `audit` / `provenance` / `tasks` 账本。

**记录结构**：

```json
{"seq": 42, "timestamp": "2026-10-26T03:20:06Z", "prev_sha256": "…",
 "tool": "a2a_send", "actor": "dev-org", "workspace": "example",
 "arguments_sha256": "…", "ok": true, "exit_code": 0, "sha256": "…"}
```

- `seq` 跨日单调递增，不重置；
- `prev_sha256` 与自身 `sha256` 构成链；
- 只记参数哈希，不记原文；
- 字符串由 JSON 序列化，换行自动转义，防止日志注入。

**控制**：

- 追加写；跨进程锁（POSIX `fcntl.flock`，Windows `msvcrt.locking`），锁内读取 `seq`/`prev` 后追加，不依赖 `O_APPEND` 原子性。
- 三个锚，逐级增强：
  1. **批准锚定**：阶段批准时由人把 `audit_head` 写入 `statement`；批准本身又受产物哈希约束。
  2. **外部 file spool**：审计同时追加到 workspace 之外的受控文件，可由采集器转运。
  3. **HTTPS 推送**：推送到组织日志系统；这是唯一能防本机全量篡改与时钟回拨的方式。
- 默认启用 1、2；3 为可选配置。生产环境应指向不同主机。
- `audit verify` 检查断号、断链与哈希；`audit-head` 打印当前链头与建议的批准 `statement` 片段，**不写批准文件**。
- 审计写入失败：变更类操作（`init`、`evidence_add`、`manifest`、`a2a_send`、令牌消费）**fail closed**；只读调用降级为 stderr 警告。
- 默认不自动删除；按日切分，链跨文件继续。清理必须显式配置。
- 时间使用 UTC；本机时钟回拨只有外部主机 sink 或签名时间戳能发现。

**剩余风险**：

- 未配置外部 sink 时，整链重写不可发现。
- 同盘 spool 不防磁盘级篡改。
- 本机时钟可被回拨。
- 审计是线索，不是证据，不参与门禁判定。

### T10 协议解析与实现缺陷

**场景**：畸形 JSON、超深嵌套、重复键、编码攻击。

**控制**：
- 严格 JSON 解析，拒绝非对象请求、重复字段与超限结构。
- 不使用 `eval`、`pickle`、动态导入。
- 只使用标准库的 `json`、`tarfile`/`zipfile`（安全解包封装）、`http.server`、`ssl`。
- 所有错误返回结构化错误，不泄露路径与堆栈给对端。

**剩余风险**：标准库自身缺陷。缓解：及时跟进 Python 安全更新。

### T11 任务生命周期滥用

**场景**：无限重试、任务堆积、取消语义不清。

**控制**：
- 任务状态机：`submitted → working → input-required → completed|failed|canceled`。
- 任务 TTL 与最大重试次数。
- 取消可被对端拒绝，但本地立即停止等待并记录。
- 任务账本持久化，重启可恢复。

**剩余风险**：对端不遵守取消语义。

### T12 协议版本漂移

**场景**：对端使用不同规范版本，方法名、状态枚举或 card 字段不一致；或我们跟随“最新”导致历史审计无法归因到当时的规则。

**控制**：

- 同时锁定 `protocol_version` 与 `spec_revision`（来源 URL、获取日期、SHA-256 或 git commit），记录在 `references/a2a.md` 与代码常量中。
- 单版本部署：一个实例只提供一个规范版本；不做多版本并行服务，不写“兼容别名”。
- 客户端发送前校验版本；服务端对未知版本返回 `UnsupportedVersion`，不猜测、不降级。
- v1 只实现非流式最小集：agent card、`message/send`、`tasks/get`、`tasks/cancel`；card 声明 `streaming: false`、`pushNotifications: false`。
- 测试断言 agent card 声明与代码常量、方法名、状态枚举一致。
- 升级流程：记录规范 → 更新常量与 card → 差异审查（方法、状态、part、安全方案、card 字段）→ 安全方案变更则重新评审威胁模型 → 协调窗口升级 → 回归入站隔离与签名校验测试。

**剩余风险**：第三方可能扩展字段；未知扩展一律不解析、不参与安全判断。

## 6. 明确不做

- 不提供生产级 IAM、密钥托管、证书签发。
