# 需求模式：核工程领域参考

> 参考性材料；不参与门禁判定。

## 好的需求句法

每条 REQ 使用：

```text
在 <适用条件/输入范围> 下，<系统/模块> 应 <可观察行为>，
使 <指标> 满足 <数值判据与方法>，依据 <来源>。
```

避免"快速、准确、稳定、鲁棒"等无指标词；无法量化时写入 `open_items` 并停止关键分配。

## 必填维度检查

- **来源**：用户需求、法规/标准条款、物理分析、基准题或设计约束；来源必须可追溯。
- **理由**：说明为什么存在，避免"因为客户要求"这类无信息陈述。
- **安全类别**：与策划阶段的安全分级一致。
- **验证方法**：test / analysis / inspection / demonstration 之一，且与验收准则一致。
- **确认需求**：需外部/独立确认的条目明确 `validation_required`。
- **接口**：数据、单位、坐标系、符号、精度、异常与兼容性。

## 常见反例与修正

| 反例 | 修正方向 |
|---|---|
| "求解器应准确计算 keff" | 指定基准题、能群模型、偏差阈值与比较方法 |
| "支持瞬态计算" | 指定时间积分方法、时间步范围、CFL/稳定性判据与测试场景 |
| "热工水力模型应稳定" | 指定守恒残差、压力/温度振荡阈值、边界条件与负向算例 |
| "使用核数据" | 指定库版本、加工链、温度点、能群与校验和 |

## 需求分配提示

- 每条 REQ 至少分配到一个 DES；未分配必须在 `open_items` 说明。
- 验收准则必须能在 test 或 V&V 阶段产生真实证据；不能把"测试通过"当唯一准则。
