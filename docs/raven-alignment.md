# 参考 Raven 的取舍：采纳了什么、拒绝了什么

本文件记录一次"参考 [EverMind-AI/Raven](https://github.com/EverMind-AI/Raven) 完善本项目"的评估结论。
它存在的理由很实际：下一个读代码的人不必把 Raven 再读一遍，也不必重新论证为什么这里没有 DAG 调度器。

判断标准只有一条，来自本项目自己的 [设计原则](../nuclear-dev-agent/docs/000-philosophy.md)：
**采纳的东西必须降低人的注意力成本，或者提高审计可信度；两者都给不了的，不进门。**

## 一、Raven 是什么

Raven 是"harness 的 harness"：宿主 raven 掌管回合循环、权限门、内置工具、记忆与 agent 名单，
每个被派活的 agent 是骑在这套循环上的第二层 harness。与本项目直接相关的几处：

| 部分 | 它解决什么 |
|---|---|
| `docs/TRACING_STANDARD_API.md` | 轨迹标准：span 树、点分属性名、关掉即空操作、错误不越界 |
| `docs-site/docs/orchestration.md` | DAG 编排：节点、依赖、路由、并发派活 |
| `agents/BUILDING.md` | 从零造一个 agent 的十分钟手册：`doctor`、冒烟、注册表与逐文件职责 |
| `docs/memory-plugin-architecture.md` | 记忆的插件化架构 |
| `evolver/` | 自我演化闭环：诊断失败轨迹 → 设计候选 → 筛选 → K=3 确认 → 三道门 → 采纳 |
| 仓库治理 | `CONTRIBUTING.md`、`CHANGELOG.md`、PR 模板、约定式提交、依赖机器人 |

## 二、采纳

### 1. 门禁运行轨迹（trace）

采纳 Raven 的轨迹**纪律**，不采纳它的**管线**：

- span 树 + 点分语义名（`gate.<阶段>`、`stage.check.<阶段>`）；
- 一次运行一个记录，记录自校验（`record_sha256`）并串成链（`prev_record_sha256`）；
- 三条硬保证原样保留：**关掉即空操作**、**写失败不改判定**、**导入即安全**；
- "轨迹是线索不是证据"——与 Raven 的 `raven.tracing` 只做观测、不做判定的定位一致。

落地形态不同：Raven 把它做成库 + 查看器 + 导出器，本项目只做成**一个标准 + 一个 CLI**，
因为本项目离线运行、只用标准库，且产物完整性已由证据哈希与批准摘要覆盖。

标准见 [skills/nuclear-dev/references/tracing.md](../skills/nuclear-dev/references/tracing.md)。

### 2. 体检（`doctor`）

采纳 `agents/BUILDING.md` 里那个"文件夹自己检查自己"的动作：一条命令给出**一次结论**，
而不是让用户把 `status`、`validate`、审计校验、版本探测各跑一遍再自己拼。

本项目加了本项目自己的含义：体检的 `ok` 是"这处工作区是完好的"，**不是**"七个阶段都通过了"。
未开始的阶段是进展事实，不是故障；健康状态不占篇幅。

### 3. 仓库治理

采纳 Raven 的工程习惯，只取对本仓库真有用的四件：`CONTRIBUTING.md`（含"加一个阶段要改哪几处"）、
`CHANGELOG.md`、PR 模板、以及把"门禁规则只有一份"写进贡献流程。

## 三、拒绝，以及理由

拒绝不是"Raven 不好"，而是**与本项目的领域约束冲突**，或者**在离线确定性条件下无法诚实地做到**。

### DAG 并发编排

Raven 用 DAG 表达"多条并行工作流 + 显式依赖"。本项目的七阶段是**门禁强制的全序**：
`nuclearlib.stage_gate` 递归检查前置阶段，前一个阶段不被接受，后一个阶段连判定都不做。
这不是实现细节，而是核能软件研发的受控要求——需求未基线化就设计、设计未完成就实现，
本身就是审计缺陷。把阶段装进 DAG 会给出"可以并行"的错误暗示，而门禁并不允许。

真正存在的图是**追溯图**（REQ→DES→MOD→TEST→VV→REL），它已经在
`.nuclear-dev/traceability.json` 里，并由 `validate` 与门禁逐条校验。要可视化，读那张图即可，
不需要第二个编排概念。

### 记忆的插件化架构

Raven 的记忆是插件化的，因为它的宿主要在不同产品形态里复用同一套记忆能力。本项目只有一个
`nuclear-dev-agent`，记忆是它的一个模块（`src/core/memory.ts`）；为一个实现造插件边界，
只会多一层要看懂才能改的间接。

### evolver 的自我演化闭环

Raven 的 evolver 是"改动→评估→采纳"的正规闭环：先诊断失败轨迹，再设计候选，廉价筛选，
K=3 确认，三道统计门，最后才采纳。**方法值得尊重，但本项目现在做不到诚实版本**：

- 采纳门槛依赖**统计显著性**与**留出测试集**，也就是要真实跑大量 LLM 评测；本仓库的 CI 必须离线、
  必须确定性，做不到；
- 用规则去给提示词打分，得到的数字看起来像证据，其实不是——那正好是本项目最反对的东西
  （"不能把静态文件说成门禁通过"）。

因此本项目只采纳它的**一半**：改动必须先在固定用例集上被评估才能采纳——这件事由 `tests/` 承担，
本轮新增的 [tests/test_trace.py](../tests/test_trace.py) 与 [tests/test_doctor.py](../tests/test_doctor.py)
就是先例。轨迹为将来的"失败轨迹诊断"留了口子：真要做，输入已经在 `.nuclear-dev/traces/` 里了。

### 多 agent 注册表与 agent 目录树

Raven 的 `agents/<name>/` 是**可发现、可派活、可独立安装**的目录约定，因为它的宿主要在运行时
扫描、调度外部 agent。本项目的七个阶段智能体是**同一宿主内的提示词段落**，不是可安装的独立进程：
一个工单一次只由一个阶段智能体做，会话与工作树都不拆（见
[010-stage-agents.md](../nuclear-dev-agent/docs/010-stage-agents.md)）。给它们造目录注册表，
只会让"谁在干活"从一张表变成两处真相。

## 四、结论

- 采纳：轨迹纪律、体检、仓库治理；
- 拒绝：DAG 编排、记忆插件化、evolver 评测闭环、agent 目录注册表；
- 本轮不做但已留口子：失败轨迹诊断（输入已在 `.nuclear-dev/traces/`），跨工作区轨迹汇总。

采纳的三项都不改变门禁判定：轨迹不参与判定，体检只转述判定，治理文件不碰规则。
`nuclearlib.py` 仍是唯一事实来源，批准仍只能由人签。
